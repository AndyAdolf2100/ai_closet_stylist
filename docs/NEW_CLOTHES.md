## 用户确定的行为

| 情况 | 行为 |
| --- | --- |
| 手动开启「邂逅新衣」 | 后续搭配允许个人衣橱＋系统参考款，开启本身不发送搭配请求 |
| 本人明确要求衣橱之外、尚未拥有的搭配 | 自动勾选；通过当前六人格的message提示后继续同一请求，不增加通用确认 |
| 个人候选不足以完成搭配 | 在回复末尾展示「添加衣物」「开启『邂逅新衣』」双入口，由用户选择；不足本身不自动开启 |
| 只想旧衣新搭／新鲜感，或否定、引用、举例 | 不自动开启 |
| 明确只用已有衣物 | 当轮回到个人来源；冻结系统款存在时拒绝局部修改，保留原记录，不偷偷替换 |
| 纯文字、原理、闲聊、纯天气 | 保留既有意图边界，不因开关而强行查询商品 |
| 衣橱读取失败 | 说明失败，不将失败解释为缺衣，不展示误导性缺衣卡 |

默认关闭、当前会话保留、历史恢复已保存轮次的状态，新对话关闭；换号／退出清理。用户手动关闭优先于会话旧状态；当轮新的明确新衣请求可再次自动开启。旧source参数和旧任务不构成授权。

引导卡添加衣物复用现有选图、预览与明确确认上传流程。开启入口续接当前搭配上下文，保留未发送草稿与尚未使用的上传锚点；校验账号、会话、版本及卡片仍在页面中，旧卡片不能跨会话操作。已开启仍不足时仅保留添加入口，避免重复提示开启。

## 提示与来源展示

自动提示按当前角色选择，无虚构共同经历或默认恋爱关系。例如冷静可靠：

> 已为你开启「邂逅新衣」。我会把衣橱之外的参考款也纳入选择，陪你找合适的新搭配。

其余五种文案见 `stylist/new_clothes.py`。流式阶段先更新开关、显示现有message；最终回执作为断线补偿，按请求ID去重。历史回放只恢复开关，不重复弹出旧提示。

系统款在搭配总标签和单品详情中标明「参考款 · 未确认拥有」，不冒充个人库存；有真实系统商品不代表有购买链接、当前库存或已核实价格。用户要求全部为新款时提示词优先全系统候选，不足须说明，不编造单品。禁穿、性别、天气、冻结、预算校验仍适用；当前系统价格未知时不能保证新增购买预算。

组合图保存允许本账号已保存结果里的混合来源，仍按账号／会话／版本隔离。系统图片同源读取须先校验商品实际出现在当前账号该轮搭配中，再重读商品身份及白名单CDN图片；不做任意URL代理。浏览器抠图／组合缓存键包含来源，避免个人与系统商品ID相同发生碰撞。此过程不把系统款录入个人衣橱。

试穿继续走原有报价和独立积分确认；通知文案区分搭配保存与衣物入柜。本次未执行任何真实试穿或扣费。

## 接口与实现

- `ChatRequest.new_clothes: bool | null`：显式开关。省略时仅继承本会话已保存的新字段，不继承旧task.source；省略字段保持旧幂等摘要兼容，true／false参与摘要。
- `Plan.new_clothes_intent / new_clothes_evidence`：本轮意图及原话证据；程序继续校验直接表达、否定、引用、纯文字等边界，模型source本身不授权。
- `Reply.new_clothes / new_clothes_auto_enabled / new_clothes_notice / wardrobe_gap`：保存有效状态、自动开启回执及引导依据，旧回复默认关闭。
- `retrieve(..., allow_system=False)`：调用方必须提供已核验授权。开启时同时读个人衣物及有限系统候选；旧source参数不能绕过。
- 系统候选采用固定签名VikingDB系统知识库召回（原Agent的legacy配置），按分类与性别检索；未配置时兼容可选MCP，必要时回退最多3页系统商品列表。详见最新集成章节；不能以模拟代替真实接口／模型验收。
- 系统图片读取：`GET /stylist-api/conversations/{cid}/catalog/{product_id}/image-source?version=...&kind=original|cutout`，须登录、当前账号保存结果及实际商品匹配。

入口代码：`stylist/new_clothes.py`、`engine.py`、`retrieval.py`、`models.py`、`main.py`、`composition.py`、`wardrobe_image.py`、`static/app.js`、`static/index.html`。
