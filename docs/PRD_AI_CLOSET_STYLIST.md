## 2026-11-05 付费界面同源与正式 H5 入口

以本地 `payment-design/index.html` 为付费视觉基准，App 与独立预览共用 `payment-views.js` 和 `payment-views.css`；顶部 message 继续使用 H5 原有 `CompanionSettings.notify`。替代旧版在 App 内另写简化弹窗、跳转另一套购买演示布局的实现。主 App 页面和导航保留，付费视图使用隔离样式，避免受到聊天页通用 article/header/footer 样式影响。

- **正常入口**：[打开 App](http://127.0.0.1:8466/app/?design=yijian#home) 无需演示参数即可挂接付费提示。现有衣物上传容量、数字分身和试穿请求返回 `product_upload_capacity_exhausted`、`digital_twin_points_insufficient`、`tryon_points_insufficient` 时显示对应面板；账号归属校验后才处理。Agent 接受 `agent_points_insufficient`／`points_insufficient` 的客户端分支已接，当前服务端未证实会返回该码，不能称真实对话扣积分已完成。
- **每次执行前查询积分**：统一通过带身份只读 `GET /stylist-api/app/points` 转发已有 `GET /api/vip_center/points_detail`，只读取 `total_available`；不再用个人资料 `vip_info.total_points` 或人物概览 `available_points` 判断可用余额。每次用户确认人物生成／试穿前重新查询，不使用缓存；有明确报价时比较 `total_available >= points_cost`。查询失败、字段缺失／非法或余额不足均停止，不把失败当0，不自动发起生成，保留待确认报价。后端在当前两个已启用扣积分执行路径前独立复查，取消、报价查询与状态读取不触发扣费。实际扣款仍由上游原子校验，余额预查不等于预留额度。
- **对话预检边界**：H5每次发起对话请求前重新查询余额；无固定报价时只阻止余额为0或查询失败，不虚构本轮费用，也不宣称正余额一定覆盖最终token消耗。没有新增服务端Agent扣费账本。尚未启用的润色执行接口不得被当作已完整接入；后续启用时必须沿用相同预检规则。
- **数据边界**：正常入口不合成余额、费用或到账成功。错误响应没有准确金额时显示“以最新报价／账户查询为准”；会员状态无法确认时不推荐重复购买会员，容量不足引导核对权益及帮助。业务报价、用户显式确认和服务器扣费守卫保持原流程，不自动重试任务。
- **演示入口**：`payment_demo=1` 只增加示例入口，方便对照润色、数字分身、试穿、Agent、容量、会员不足及购买返回。示例金额只用于演示。正常入口没有这些演示按钮，也没有“体验到账”按钮。

## 1. 产品定位与目标

一位能记住当前要求、优先使用已有衣物、解释具体穿法的私人搭配师。先帮助用户穿得合适、舒服，再提供符合个人接受程度的新意。

衣衣通过自然语言对话提供服务，支持原创男女搭配师形象及对应回复人格，具体要求见第13章。角色负责陪伴和传达真实执行状态，穿搭建议仍以用户条件、真实衣物及可用天气为依据。

核心价值：

- 贴心：尊重禁穿条件、步行需求和预算，不默认身材焦虑，不反复要求用户重述。
- 专业：结合场合、温度、材质、比例和实际穿法说明理由；未知信息不编造。
- 可执行：区分真实衣橱单品与文字参考，能从完整方案连续修改到用户满意。
- 有启发：在基础方案上提供有依据的新意，帮助用户理解并迁移到自己的衣橱。

首版不以购物导购为主要目标，不以推销试穿或会员代替穿搭建议。

### 1.1 目标用户与使用前提

当前面向已有 AI Closet 账号、希望获得日常穿衣建议的用户，尤其适用于有个人衣橱数据、需要按场景选衣或反复调整穿法的人。首批用户的年龄、性别比例、地域和重点场合尚待补充，不将现有女性角色形象解释为仅服务女性。

纯咨询可以基于用户口述衣物提供建议；真实选款需读取账号可访问的商品；整套试穿还需现有 App 中可用的人物形象。当前页面发送咨询也需要登录，并非匿名问答。

| FR17 | 搭配结果卡 | 区分真实商品方案与文字参考，包含名称、衣物、为什么、怎么穿和必要提醒 | 每次回复最多三个后续建议；不虚构库存、价格或商品性能 |

### 3.2 本版没有提供的能力

当前新页面没有单品图片上传、衣物属性编辑与删除、单品美化、单品试穿、人物分身创建、自动画像学习、传统文化配色、多角色评审、购物下单、会员充值和公开博主灵感检索入口。上游服务或相邻项目存在相关能力，不表示衣衣已接入。后续如需加入，单独补充需求与验收范围。最终搭配组合图上传OSS已按2026-10-30新需求接入，独立于单品录入／收费生图。

## 4. 核心交互流程

### 4.1 开始一次搭配

1. 用户登录，按需选择天气策略，输入自然语言需求；衣物来源固定为当前账号个人衣橱。
2. Agent 提取当前场合、时间、偏好、禁忌和已有衣物；缺少非关键条件时先提供合理方案。
3. 仅在会明显影响结果且无法安全推断时追问，例如指定衣物存在多个候选。
4. 衣物查询及推荐默认先读取个人衣橱和商品属性，按需查询天气，检查硬条件后组织方案。
5. 返回简短结论、搭配卡和最多三个具体下一步；用户可继续修改。

所有衣物推荐默认先查个人衣橱。不得把“不穿高跟鞋”等否定表达误识别成指定单品请求。

### 4.2 搭配卡内容

每张卡提供：方案名称、衣物、搭配理由、具体穿法、必要提醒。匹配到的个人衣物展示图片及来源，即使只有一件也保留；整套建议其余缺少的品类单列为文字参考。组合图只合成已选真实衣物，界面区分部分匹配和完整结构；无合规候选时明确原因，不伪造商品身份或库存。

2026-10-30 更新：真实衣物以按属性分层、适度重叠的组合图呈现，外搭在内搭之上、配饰位于最外层；展开后可选择每件衣物查看原图及有依据的属性，兼顾手机／PC 与男女主题。保留单品和文字方案不伪装成完整搭配。详见 [搭配组合设计](OUTFIT_COMPOSITION_DESIGN.md)。缺少抠图时在浏览器现场分割，当前账号原图经同源只读入口获取，结果仅本页缓存。已用五件真实原图验证Chrome推理及组合；真机和生产链路仍待验收。

穿法应包含能照做的细节，例如外套敞开或系扣、裤脚处理、鞋袜衔接、配饰位置。没有结构证据时不能断言衣服具有可拆领、抽绳或防水功能。

用户没有要求购买或试穿时，不在每轮回复中重复营销。

### 4.3 连续修改

- “再休闲一点”沿用当前场合与禁忌；明确新任务才重置。
- “只换鞋”冻结其余真实商品。无合格鞋时保留当前方案，说明本次候选不足。
- 纯原理或明确只要文字的追问继续咨询；后续具体衣物查询与推荐默认先查个人衣橱。
- 文字穿法不能凭空转换为数据库商品或可试穿方案。

### 4.4 天气与地点

提供自动查询、使用用户提供天气、暂不考虑天气三条独立路径。

2026-10-27新增：用户主动点击浏览器定位并确认城市，或手动填写城市；今日实际出行与本周文字规划均按需查预报。角色「衣衣」以Q版天气卡和出行小叮咛呈现，整体沿用奶油／绿色基调并增加克制淡粉。等待动作对应真实服务阶段，支持减少动态效果。当前仅有日夜预报，早间不编造温度；风力与能见度仍待上游补齐。详见[交付与限制](WEATHER_AND_YIYI_2026-10-27.md)。

- 不考虑天气：不调用地点和天气接口，不按默认城市筛选。
- 城市重名：提供必要的省市确认；无法查询时允许继续文字搭配。
- 登录失效、地点歧义、天气接口异常分别提示，不能都显示“地点验证不可用”。
- 天气失败时说明缺少的依据，不伪造实时温度；没有逐日数据不声称已验证全部日期。

手动选城采用省份、城市两级联动，修改省份后清空旧城市，取消选择不改变已确认城市。浏览器定位需用户主动点击；降低坐标精度后交给地理服务转换城市，精确坐标不写入对话。定位失败时提供手动选择，不阻断其他服务。

天气卡提供今日、本周、未来七天范围，按实际上游日期展示。天气背景只表达实际天气类型，不能据此推断官方预警等级。独立天气面板刷新与对话内“不考虑天气”属于不同操作：后者约束本轮搭配，不代表自动关闭用户已主动开启的城市天气面板。

### 4.5 试穿与费用

2026-11-02入口精简：首页移除 `media-open`「上传与生成记录」按钮；统一从输入区「生成记录」回看上传及生成任务，首页保留上传衣物和我的试穿形象入口。删除旧的最后一项文字按钮样式，避免误套到 `twin-open`，两项均保持主题卡片样式。

上传图片按文件真实PNG／JPEG／WebP签名设置MIME，兼容扩展名错误及浏览器未提供类型；不转换或压缩图片，保留10MB限制、后端格式校验与明确确认后提交。格式通过只表示可继续检查，不代表照片人物检查或数字人生成已通过。

2026-11-02更新：普通穿搭不再提供「先确认需求」勾选，新请求直接按用户原话执行。穿搭需要天气而目的地、上下文及页面均无城市时，展示乙游城市引导卡；明确城市、行程或忽略天气不弹卡，纯原理／闲聊／上传不问城市。点击复用城市弹窗，确认后沿用原请求和约束继续；不强制浏览器定位，不覆盖未发送草稿。已有建议不冒称包含当地天气。详见 `docs/CITY_INVITATION_QA.md`；此变更不取消下面的费用确认。

真实商品方案 → 选择并确认试穿形象 → 查看实时费用与保存影响 → 用户明确确认积分 → 提交一次 → 展示状态或结果。

费用变化、搭配变化、形象变化或确认过期，需要重新报价。同一次动作重复点击不重复派发。上游结果不明时提示查看试穿记录，不自动再次生成。

当前已验证过的报价为 2 积分/次，仅代表当次业务报价；不是固定承诺，也不是底层模型的人民币成本。实际生成、扣费及退款需要专项验收。

### 4.6 历史与账号切换

历史列表展示当前账号会话，点击后恢复已有内容和最新版本，再继续提问。新对话从新的任务开始，不能把上一套衣物或禁忌意外带入。登录失效时保留原输入和当前对话，提示重新登录；不同账号登录后清理前一账号的页面内容，历史读取和操作仍由服务端验证归属。

### 4.7 无结果与失败恢复

| 情况 | 对用户的交付要求 |
| --- | --- |
| 本次候选不足 | 保留已匹配的个人单品图片，缺少品类单列文字参考；没有合规单品才只给文字，不把有限候选等同全衣橱 |
| 局部替换无合格商品 | 原真实方案保持不动，明确没有完成商品替换 |
| 材质、价格等关键属性未知 | 不承诺已满足排除条件或预算；不擅自放宽用户要求 |
| 登录失效 | 提示重新登录，保留输入，不伪装成城市错误 |
| 城市不唯一或无法确认 | 请求必要的省市确认，不自动使用默认北京 |
| 天气不可用 | 明确当前天气依据缺失，按实际可用条件继续建议，不伪造预报 |
| 对话连接中断 | 提示未收到完整结果，允许在历史中核对，不将加载动画当作成功 |
| 试穿执行状态未知 | 提示核对已有试穿记录，不自动再次派发生图 |

### 4.8 官方预警与天气提醒

日夜温差、雨天鞋袜等穿搭提醒与官方灾害预警分开呈现。官方预警只使用已授权来源的有效数据，模型不得推断或生成红、橙、黄、蓝等级。

预警栏固定在聊天滚动区外，同时展示颜色与文字等级。多条按等级、发布时间排序，保留影响范围和原始防护正文；切换确认城市时更新，页面可见时每两分钟查询，重新进入页面时刷新。未登录不查询；历史天气不能覆盖当前城市预警。

未配置、超时、过期或部分数据无效均应说明不可用或不完整，不能解释为“没有预警”。当前真实预警数据源未接通，真实页面应明确提示这一状态。详见[气象预警与省市联动](WEATHER_WARNINGS_AND_CITY_PICKER.md)。

## 7. 免费与付费设计

### 7.1 当前实际规则

文字咨询、选款、修改、多日文字规划没有新增会员门槛或文字积分扣减；需有效登录，同一会话处理期间阻止并行覆盖。项目尚未设置完整的按用户每日额度和速率限制，服务端仍承担模型调用成本并受上游额度约束。

图片试穿沿用现有服务的实时报价和积分扣减；新 Agent 不维护另一份余额。

### 7.2 商业化规则，新增交互与计费待实现

2026-11-05 当前付费交互基线（用户确认沿用现状）：Agent积分不足同时展示对话卡片与顶部message，点击卡片按钮或message阅读入口打开角色来信，再从来信进入积分方案；非Agent不再要求“只弹message”，数字分身直接打开分身费用／不足面板，合成试穿直接打开积分补充面板，容量不足直接打开容量权益面板。正常任务费用确认保留，不自动购买或重试任务。图片润色与会员专属不足面板已有预览，尚不能据此宣称真实业务入口已完整接入。角色文案跟随当前人设与昵称。Agent输入、输出分别累计，每满100万token各扣300积分，余额最低0；该累计结算仍待Server实现。真实商品购买、后台会员权益和到账仍未完成，不因确认交互现状而标记已完成。

以下旧建议仅作历史参考，与上述当前规则冲突时不再适用。

| 层级 | 建议保留内容 | 原因 |
| --- | --- | --- |
| 基础体验 | 穿搭咨询、基础衣橱搭配、当前方案修改、必要天气与禁忌检查 | 用户应能完成一次有价值的穿搭任务 |
| 成本型增值 | 试穿生图、额外图像版本 | 与可计量成本对应，逐次明确确认 |
| 深度服务 | 可编辑多日计划、周期衣橱整理、长期风格复盘 | 按交付深度收费；需先补齐能力再设计权益 |

不把安全、舒适、准确性作为付费解锁项，不靠降低免费建议质量促成付费。免费额度、会员价格和积分兑换比例暂不定价，需依据真实账单、使用频率和付费意愿评审。

对外开放前增加按用户与系统总量的调用预算、频率限制、清晰的额度提示；避免一次对话触发无界搜索或生图。

### 8.2 当前固定使用的业务 REST 接口

下表路径均相对于 AI Closet Go 服务。认证与应用版本由后端适配，浏览器不直接持有模型或天气供应商密钥。

| 接口 | 调用时机与用途 | 认证与业务影响 |
| --- | --- | --- |
| `POST /users/app/login/mobile/code` | 本地页面提交手机号、验证码后获取现有登录态 | 手机号按已有 RSA 公钥约定加密，包含版本和设备信息；可能因现有单点登录规则使旧页面失效；生产关闭本地代理 |
| `GET /api/user/info` | 每个受保护业务请求确认可信账号身份 | 用户 Bearer、`version`、`device`；客户端提交的用户 ID 不作为授权依据 |
| `GET /api/user_product/quick_edit_list` | 个人衣橱选款、本人图库导出 | 分页读取本人正常衣物；推荐当前最多三页、每页 50 件，导出采用独立分页；参与 AI 搭配标志仍有上游过滤缺口 |
| `GET /api/product/list` | 用户允许系统商品且语义工具不可用时补充候选 | 用户 Bearer；当前回退只读第一页 50 件，不代表全库覆盖 |
| `POST /api/weather/get_weather` | 天气卡、指定日期及多日穿搭的预报读取 | 传权威确认后的省、市及 `days=14`；虽然使用 POST，业务语义为只读；仅使用返回的实际日期 |
| `GET /api/memories` | 服务连接检查中的只读接口探测 | 仅为旧上游探测，不用于本项目手记；本项目手记路径为 `/stylist-api/memories`，见 LONG_TERM_MEMORY.md |

当前不使用存在界面状态变更副作用的旧商品详情入口或 `user_all_list` 作为常规召回方式，避免一次选衣操作意外清除原 App 的提示或修改排序。

### 8.4 外部请求的数据与费用要求

1. 模型收到必要的对话、当前任务和候选商品文本属性，不收到业务 Bearer、供应商 Key、登录验证码或精确坐标。当前选款主要依赖文本属性，不将其宣传为已完成衣物图片视觉识别。
2. 业务 REST 与 MCP 使用当前账号登录态；地理服务只收降低精度的位置；预警服务只收确认后的城市、省份及其独立服务 Key。不同依赖不混用凭证。
3. 只有用户确认整套试穿后，才允许保存搭配并请求图像生成。只看报价、取消生成、检查连接不执行生图扣积分，但模型连接检查仍会发起一次真实小模型请求，可能产生成本。
4. 当前报价确认有效期为五分钟。提交前复核搭配版本、人物形象、工具契约与积分价格；变化后重新确认。上游未提供原子锁价参数，跨服务价格竞态仍需生产化补齐。
5. 地理解析当前有进程内缓存和请求间隔，多日预报当前缓存十分钟。外部超时、缺失字段或目录变化时提供明确降级，不把错误解释为无库存、无预警或没有天气风险。
6. 供应商实际合同、人民币单价、模型具体版本、图像底层供应方、预警授权和生产限流需后续补充；不以当前开发配置或单次报价替代商务与生产承诺。

## 10. 验收标准与评测

以下为目标标准，不是当前全部达标的声明。

| 验收项 | 通过条件 |
| --- | --- |
| 原否定表达回归 | “不穿高跟鞋”不触发指定单品失败，合格方案不含高跟鞋 |
| 天气策略 | 选择不考虑天气后不查询地点或天气；无默认城市干扰 |
| 任务延续 | 后续修改保留已有禁忌与场合；明确新任务后更新正确 |
| 局部冻结 | 只换鞋时其余商品 ID 不变；找不到时不偷偷换整套 |
| 商品真实性 | 所有可操作商品来自当前合法候选，个人与系统来源不混用 |
| 缺失属性 | 未知材质、价格或鞋跟不被自动解释为符合限制 |
| 异常恢复 | 鉴权、地点、天气、无候选分别解释，并提供可行下一步 |
| 跨用户隔离 | 无法读取或操作其他账号会话、导出与图片动作 |
| 费用安全 | 未确认不派发生图；同动作至多派发一次；价格变化重新确认 |
| 来源可信 | 无可验证来源不编造博主、链接或访问结果；无授权图片不进入图库 |
| 城市选择 | 更换省份清空旧城市；取消不改已确认城市；定位被拒仍可手选 |
| 预报日期 | 今日、本周和未来七天按返回日期匹配；缺失日期明确标识；无早间逐小时数据不展示早间卡片 |
| 官方预警 | 过期、解除、跨城市数据不作为当前预警；未接通不提示“无预警”；演示数据不进入真实栏 |
| 陪伴与进度 | 表情和进度对应实际阶段，系统减少动态效果设置生效，不影响正文可读性 |
| 第三方凭证 | 业务 Bearer 不转发地理服务、预警独立服务或图片 CDN；供应商 Key 不进入页面与对话 |

建议建立至少 30 条代表性多轮场景，覆盖通勤、看展、婚礼、步行、雨天、禁忌、指定单品、无候选及局部修改。硬条件违反、越权与重复派发均要求零次；审美由人工按贴心、专业、可执行、新意四项各 1—5 分盲评，首轮目标均值至少 4 分，记录分歧原因。

上线后观察首次可用方案率、必要澄清轮次、修改成功率、方案满意度、生成成功率、每个满意方案成本及投诉原因。记录业务事件与匿名统计，不在分析日志保存密钥、手机号或完整私人对话。
